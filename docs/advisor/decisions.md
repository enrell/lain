# lain server decisions (citable in plans)

Use these IDs in plans and advisor calls: `D-001`, etc.
Update this file when the user answers a `needs-user` question.

## Stack and build

- `D-001` — Prefer the Go standard library. The only three justified dependencies are `golang.org/x/crypto` for bcrypt, `golang.org/x/term` for login, and `go.etcd.io/bbolt` for `lain.db`. A new dependency is a permanent cost and must be discussed first. Source: `AGENTS.md:6`.
- `D-002` — No cgo and no large C-transpiled dependencies. Builds must remain measured in seconds. Source: `AGENTS.md:20`.
- `D-003` — Use standard-library `net/http` method patterns without an HTTP framework. Source: `AGENTS.md:14`.
- `D-004` — Store data in bbolt through `internal/kv` using JSON values and composite keys in the `users`, `libraries`, `items`, `progress`, and `meta` buckets. Keep `internal/store` only for operator configuration and legacy import. Source: `AGENTS.md:15`.
- `D-005` — Use HS256 JWT in `internal/auth`, implemented with standard-library HMAC/SHA-256 and live role, liveness, and password-version checks. Source: `AGENTS.md:18`.

## Boundaries

- `D-006` — Plugins implement `core.Provider` and never touch `net/http`, process-global state, or another plugin's files. Source: `AGENTS.md:33`.
- `D-007` — Media bytes never enter plugin calls; the gateway streams from disk. Source: `AGENTS.md:35`.
- `D-008` — Catalog owns identity and userstate owns progress; never merge them. Source: `AGENTS.md:36`.
- `D-009` — The `merge-many` and `fan-out` modes belong to the metadata slice and must not be repurposed early. Transcode, metadata daemon, and Matrix daemon work begin only in their explicit slices. Source: `AGENTS.md:28`.

## Hygiene and discipline

- `D-010` — Never commit real release-group, fansub, tracker, indexer, or site names. Use fictional placeholders such as `[Fansub-A]`, `[Fansub-B]`, and `tracker-example`. Anime titles are allowed; group identities are not. Source: `AGENTS.md:42`.
- `D-011` — Use typed errors with stable `core.Error` codes; never panic on bad input and never fail silently. Source: `AGENTS.md:26`.
- `D-012` — Work in small slices and keep `go test ./...` green for behavior changes. Source: `AGENTS.md:24`.
- `D-013` — This repository is the server; the desktop client lives in `projects/lain-desktop`. Do not mix their commits. Source: `AGENTS.md:68`.
- `D-014` — English is the only canonical repository language for code, comments, tests, plans, project documentation, contributor instructions, and wikis in both repositories. Non-English content is limited to explicitly identified translations, localization resources, and language-specific documentation variants. Source: interview 2026-09-11.

## Transcode evolution

- `D-028` — Add asynchronous transcoding as `lain.playback.transcode@2` while retaining the synchronous `@1` contract and GET endpoint. Playback inspection is side-effect free and reports an opaque session plus `idle|queued|running|ready|failed`; only an authenticated POST starts or joins work, and an item-scoped status endpoint exposes state without filesystem paths. Source: user answer Q-017/A + advisor triage, 2026-09-13.
- `D-029` — Bound ready transcode artifacts with a plugin-private 20 GiB LRU cache, configurable by `--transcode-cache-size` / `LAIN_TRANSCODE_CACHE_SIZE`. Metadata uses atomic sidecars; cleanup runs at startup and around admission/completion, excludes active artifacts, and removes stale-source and abandoned-temporary entries without coupling the plugin to library deletion. Source: user answer Q-018/A + delegated engineering choice + advisor triage, 2026-09-13.
- `D-030` — Browser compatibility becomes probe-driven and applies equally to anime, movies and series: direct-play only verified web-safe streams; otherwise produce one conservative SDR H.264/AAC MP4, with selected stream identity in the session/cache key. Add selectable audio first, then convertible text subtitles as WebVTT sidecars; reject HDR and unsupported subtitle tracks explicitly until separately scoped tone-map/burn-in profiles. Source: user-delegated engineering choice Q-019 + advisor triage, 2026-09-13.
- `D-031` — Keep progressive MP4 with HTTP Range as the delivery protocol. HLS/DASH, ABR ladders and hardware acceleration stay deferred; future hardware support must be explicit operator opt-in with capability probing and visible software fallback, never silent opportunistic switching. Source: user-delegated engineering choice Q-020 + advisor triage, 2026-09-13.

- `D-039` — `lain.playback.transcode@2` gains one additive status field, `progress` (0..1, omitempty), present while a job runs; no version bump and no server-side ETA promise — the client derives elapsed time and pace from deltas. The field is additive but the @2 payload had been fixed by D-028, so it ships only under this explicit answer. Source: user answer Q-027/A, 2026-09-17.
- `D-040` — The AV1 wait is not paid by weakening the frozen profile: `web-mp4-sdr-v2` / `veryfast` / software-only stays exactly as D-030/D-031 fixed it. The wait is instead reserved to its own slice, authorized but not started: browser-capability direct play, where the client reports decoder support and a verified source remuxes (AV1/Opus into MP4 plus a WebVTT sidecar) instead of re-encoding. That slice needs its own plan before any code. Source: user answer Q-028/C, 2026-09-17.
- `D-041` — Preparation stays play-triggered: only the player's authenticated POST starts work (D-028 intact); no details-page CTA and no proactive warm after scan. Source: user answer Q-029/A, 2026-09-17.

- `D-047` — Close the last gaps found in the second audit pass, still inside the approved `@3` shape: (a) on-the-fly subtitle extraction — `@3` gains a `subtitles` action and a sidecar-only delivery kind, so `GET /api/items/{id}/subtitles?stream=N` serves WebVTT for a **directly played** file without transcoding it (Jellyfin's "allow subtitle extraction on the fly"), gated by the new `allow_subtitle_extraction` setting (nil/absent = on, explicit false → `forbidden`); image-based tracks stay `unsupported-media`. - `D-048` — The gateway signs HLS media URIs, not the plugin: serving `index.m3u8` rewrites the `EXT-X-MAP` URI and every segment line to carry `session` and the caller's `token`. Keeping the rewrite in the gateway preserves D-006 (the plugin never handles tokens or HTTP) and D-043 (no new dependency), and the `?token=` model is unchanged. (b) `artifact_root` already carried the `lain-transcode` namespace, so reopening a finished relocated session from its sidecar resolved a doubled `lain-transcode/lain-transcode/<session>` path; `pathsFor`/`pathsForEntry`/`removeArtifacts` now share one meaning for the owned root. - `D-051` — The visible software fallback must clean the burn-in filter graph too: `softwareFallback` stripped `hwupload`/`format=nv12` from `plan.filters`, but the image-subtitle path bakes those tokens into `plan.complexFilter`, so a VA-API session that both burns in an image subtitle and fails its hardware attempt retried with the hardware upload chain and failed again. Every fix carries a regression test; the client-side one was proven by reverting it. Source: adversarial audit passes 1–8, 2026-09-18.
- `D-053` — Three Jellyfin-documented options complete the encoding surface, additive and inside the `@3` shape (no frozen payload touched): `hls_segment_container` (`fmp4` default, CMAF with an init segment; or `mpegts`, classic `.ts` with no `#EXT-X-MAP`), `hardware_low_power` (QSV's low-power H.264/HEVC encoder, honoured only by QSV), and the AV1 preset now reaches the argv (it was exposed and validated but hardcoded). `TranscodeProfileKey` gained the output-affecting inputs it was missing — `hardware_decode_codecs` and `ffmpeg_path` — while the VA-API render device stays operational and out of the key (D-045/D-050). Everything is probed with a real ffmpeg where the local build allows it. Source: Jellyfin feature-parity audit, 2026-09-18.
- `D-054` — Hardware (VPP) tone mapping is **deliberately not implemented**, and the gap is documented in `docs/CONTRACTS.md` rather than shipped unverified. Concrete evidence from the local ffmpeg: `vpp_qsv` exposes **no `tonemap` option** (only deinterlace/denoise/detail/procamp/crop/scale), so Jellyfin's QSV chain (`vpp_qsv=tonemap=1`) cannot work here regardless; and `tonemap_vaapi` needs VA-API device/frame plumbing (`-init_hw_device`/`-filter_hw_device`, or hwaccel-surface frames) that cannot be validated without a device (the probe finds no backend on the dev host). A wrong chain would fail at runtime and then hit the same fallback-stripping pitfall as D-051 (the software retry must replace the hardware filter, not replay it). The software `zscale`+`tonemap`/`libplacebo` chain already produces correct SDR output, so the missing feature is speed, not correctness. Source: user mandate "all features" + the honest-limitation discipline, 2026-09-18.
- `D-055` — Three corrections close the last documented gaps of the D-042 transcode slice; none touches a frozen payload or the `@3` shape. (a) The served HLS playlist dropped the `#EXT-X-DISCONTINUITY` ffmpeg wrote — the parser even attributed it to the *previous* segment, where HLS places it *before* the segment that starts the new timeline — so a client could stitch across a timestamp jump; the tag is now attributed to the following segment and re-emitted between segments (and dropped when segment deletion moves that boundary to the front of the playlist, where nothing precedes it to be discontinuous from). (b) `position` was a high-water mark, so after a rewind ffmpeg kept racing ahead and the deleter removed the very segments the client was about to re-fetch; the latest report now wins, matching Jellyfin's use of the reported playback position. An out-of-order report can only make the position older, which errs toward pausing sooner and keeping more segments — never toward deleting or racing ahead of the viewer, so the ordering robustness the high-water mark bought is not lost. (c) The browser direct-play profile accepted only AAC audio inside MP4; MP3 is equally web-safe and now direct-plays too, while AC-3/E-AC-3 stay excluded because Chromium on Linux cannot decode them (D-030's "verified web-safe streams"). Each fix carries a regression test that was proven to fail with the fix reverted. Hardware (VPP) tone mapping stays deliberately unimplemented per D-054. Source: user instruction "faça as correções" on the reported gap list, 2026-09-19.
- `D-056` — The web UI becomes title-centric. `/item/{id}` was a page for one file, which is wrong for anything episodic: it is now the *title* page (hero, poster rail, season filter, episode grid), and a single-file title keeps the plain item page. `/player/{id}` is the watch page — video with the title's episodes beside it — and the route reloads when the id param changes instead of once in `onMount`, so switching episodes cannot leave the previous episode's state or its marker on screen (the smoke asserts the in-place switch, and that assertion fails with `onMount`). The grid is served by a new additive read, `GET /api/catalog/{id}/episodes` → `{items}`: chosen over reusing `GET /api/search` (Q-033/A) so a detail page never depends on the search plugin, and implemented on the concrete catalog service the gateway already uses for `Page`/`Get`, leaving the `lain.catalog.read@1` capability untouched. One grouping rule — `catalog.TitleKey`, lowercase with collapsed whitespace, mirrored by the web `normalizeSeriesTitle` — so a show's card and its own page cannot disagree about the episode count; a title spans libraries, and watch order is season, episode, year, id rather than the raw title, which would let casing or spacing decide the order. The inline `ShowPanel` (a show page with no URL of its own) is deleted and `ShowCard` navigates, so there is one implementation instead of two. Proven in a real Chromium: two new smoke steps assert the episode grid and the in-place episode switch, and each was shown to fail with its own fix reverted. Source: user report that the detail page is episode-only + Q-033 answers, 2026-09-19.
- `D-057` — The player's seek bar spans the media, and a seek past what the encoder has written starts producing there. Root cause, verified in the hls.js source and the MSE spec: an `EVENT` playlist lists only the segments ffmpeg has already written, so hls.js sets the MediaSource duration to that edge (`buffer-controller.getDurationAndRange`, with `liveDurationInfinity` as the only escape) and, per MSE §10.1, `seekable` becomes `[0, duration]` — i.e. the produced prefix. A 24-minute episode therefore showed a 0:37 timeline. The fix has three parts, each at the layer that owns the fact: (a) the gateway adds `duration_sec` to the plan response from the probe it already runs — the same fact Jellyfin's `PlaybackInfo` exposes as `RunTimeTicks`, placed on the HTTP view so `lain.playback.plan@1` and every plugin shape stay frozen; (b) the player hands that length to hls.js through the supported `attachMedia(media, {overrides: {duration}})` (a public `MediaOverrides` field), which makes the element's duration and seekable cover the episode — safe mid-session because `endOfStream` is driven by the playlist's `ENDLIST` (`BUFFER_EOS`), never by the duration; (c) a target outside the session's own range rebuilds it at the target through `start_sec`, the mechanism a resume and a track change already use, while a target inside the produced range stays an ordinary instant element seek. The produced edge is read from hls.js on demand (`latestLevelDetails.edge`) rather than mirrored in state. The buffered region is drawn in source coordinates, so a resumed or re-seeked session no longer paints its ready range from zero. Proven in a real Chromium against a deliberately lagging transcode (a VP9 source, one thread, `veryslow`: a copy-compatible H.264 source finishes before a viewer could seek, which is why the first attempts could not reproduce it) — `seek bar spans 600.0s of a 600.0s episode` and `dragged past the produced edge: rebuilt at 420.0s and played on from there`, each shown to fail with its own part reverted (`media duration 2s`, and a session that was never rebuilt). The user delegated the placement decision (Q-034); this is the layering a senior would pick and the one that keeps the plugin contracts frozen. Source: user report "o controle (slider) do player só está mostrando o tempo do buffer" + web research into hls.js/MSE, 2026-09-19.
- `D-058` — A browser that reports what it can decode gets the file as it is. Direct play was a hardcoded container rule (D-030), so every Matroska file was transcoded on principle and a seek paid the session restart D-057 measured. Measured on this host (Chrome 152, through the gateway's existing `video/x-matroska` + `ServeContent` path): H.264+AAC Matroska opens, seeks in 93–268 ms and downloads ~11 KB of a 13.8 MB file, cues at end included; HEVC+AAC opens too — and paints nothing (no error event, an advancing clock, `videoWidth` 0x0, zero frames). The two a-priori queries disagree in opposite directions: `decodingInfo` is right about HEVC and AC-3 but false-negatives VP9+Opus, which in fact plays; `canPlayType` with a codec string cannot see a platform decoder it has no string for. So the client probes a fixed matrix once per page load, reports the **union** of both answers as tokens (`mkv`, `mkv/h264`), and the planner requires the container *and* every track a player would select to be covered. The pairing is the part that carries the weight: a flat codec list would let "HEVC decodes in MP4" license "HEVC in Matroska", which is exactly the measured black screen. `PlanRequest.Capabilities` is additive and optional — nil reproduces the old rules byte for byte, which is what the desktop, `curl` and the existing Go tests still exercise — and the gateway validates tokens against its own vocabulary, so a client cannot widen what the planner reasons about. A claim also cannot raise the H.264 High-10 floor: `canPlayType` answers "probably" for the profile bits it does not parse, so the probed pixel format decides there. Trust stops at the plan: on a `direct` plan the player demands a decoded picture within ~3.2s and falls back to a transcode at the viewer's position, saying why. Proven in a real Chromium — a new smoke step direct-plays a procedural H.264/AAC Matroska and seeks to its midpoint in **126 ms** (one Range request, against 2.6 s for the rebuild in the same run), the same file answers `direct`/`transcode` for four different claims including one naming another codec family, and a client that lies about HEVC gets a picture back instead of a black screen. Both halves were shown to be load-bearing by reverting them: with the frame check off, the lying-client step fails with "timed out waiting for the frame check started a transcode"; with the codec pairing off, the partial claim plans `direct` for an HEVC file at the wire and the suite breaks downstream. Source: user direction that 2026 browsers decode Matroska natively (with sources) + the measured matrix, 2026-09-19.
- `D-059` — The web player owns a dependency-free WebGPU shader engine, while the browser media element remains authoritative for demux, decode, buffering, seeking, A/V sync and audio (D-043/D-057/D-058 stay intact). Each decoded frame is re-imported as a `GPUExternalTexture`, normalized once into an internal `rgba16float` `GPUTexture`, processed by an ordered WGSL-native graph with explicit inputs, up to eight scalar parameters, reusable hazard-safe texture slots and `requestVideoFrameCallback` scheduling, then displayed on a canvas. WebGPU is optional: native video remains visible until the first GPU submission and takes over on initialization/runtime failure or while a browser-rendered sidecar subtitle is active. Anime4K is a future MIT-attributed shader pack, never an engine dependency; the first slice uses only original ingest/display/no-op WGSL and adds no package or server/API contract. User-facing presets, custom shader loading and settings wait until the runtime is proven. Source: user direction + advisor `answered`, 2026-09-19.
- `D-060` — With D-059 proven, ship the first opt-in shader pack as `Anime4K DoG x2`: four ordered WGSL passes (luminance, horizontal Gaussian/min-max, vertical Gaussian/min-max, bounded correction at 2x) adapted from the MIT-licensed Anime4K/anime4k-wgpu sources, with source headers and complete notices retained. The player exposes only `Off` (default) and this conservative preset; no persistence, arbitrary-file loading or advanced effects UI enters this slice. The pack remains isolated from the generic engine and adds no runtime dependency or server/API contract. Source: user direction + advisor `answered`, 2026-09-19.
- `D-062` — The admin Playback page becomes an operational control center without changing `TranscodeSettings` or any server contract: at-a-glance delivery/engine/HDR/session status, section navigation and search put common decisions first; capability diagnostics and expert resource/hardware controls use progressive disclosure but remain reachable and visibly marked when configured. `Apply Auto` stages a conservative software-safe policy using only existing values (`hls`, `fmp4`, `auto`, `0`, empty/inherit) and never saves by itself. Hardware discovered by the existing server probe is presented separately and requires an explicit backend opt-in; visible runtime fallback remains D-031 policy. Unsaved actions live in a viewport-fixed dock above the mobile navigation, so a long form never requires returning to the top to save or reset. Source: user direction + advisor `answered`, citing D-020/D-022/D-031/D-042/D-045/D-046, 2026-09-20.
- `D-063` — Hardware acceleration is capability-aware by default. On a genuinely fresh settings record, the server persists the highest-preference concrete backend that passes its real one-frame encode probe and enables hardware encoding; an explicit saved `none` remains authoritative and is never reinterpreted. `Apply Auto` mirrors the same deterministic preference and stages hardware without saving; when no backend passes, both paths use software. Runtime probe failure still falls back visibly. This narrowly supersedes D-031's opt-in default and D-062's software-only Auto policy without adding an `auto` value or changing the settings contract. Source: explicit user direction + advisor `answered`, citing D-042/D-044/D-046/D-050, 2026-09-20.

## Web player chrome

- `D-061` — The web player adopts the **Terminal Chrome** direction from the third design study (`web/design-showcase/player/`, isolation per D-021), so the watch page stops contradicting the app it lives in. The player and its route previously painted hardcoded `bg-black`/`text-white`/`bg-white/20` while every other page is drawn from the live host palette (D-020/D-037); the player now consumes only the semantic tokens, so a host theme that is not black is no longer overridden by its own player. Web-only — no dependency, no server change, no contract change; behaviour is preserved per D-038/D-056/D-057/D-058/D-059/D-060. The one deliberate behavioural change: the bar and the transport deck no longer fade with the idle timer (the track chips and the resume/play affordances still do), because a tiled layout cannot hide a row without reflowing the picture, and the seek bar must always be reachable. Evidence: the three study concepts render at 1600×900 in a real Chromium with **zero pure-black pixels** (palette-exact counts of `#151623`/`#9a778a`/`#bac5cd`/`#b4c9ab`), and the production player was driven in a real Chromium against a live progressive session — new chrome on screen, `duration 120`, `readyState 4`. - `D-064` — The watch page's chrome fades with the idle timer, in place, and the picture no longer toggles play/pause. The bar, the telemetry lines, the track chips and the transport deck are one chrome; while playing and idle it goes to `opacity-0` with `pointer-events-none`, and it wakes on a pointer move near the chrome, on any pointerdown (a click on the picture included), on `focusin` inside it, and on the keys that already revealed it. It is never unmounted: the rows keep their place, so the picture cannot reflow and the zones the pointer has to find cannot slide away from it — which is exactly the constraint `D-061` recorded, so this supersedes only that decision's no-fade clause and not its no-reflow premise. The zones are measured from the real elements (`getBoundingClientRect()` plus a 56px margin), never a hardcoded height. The timer is pinned — the chrome stays — while paused, during a scrub, while the preparation overlay, an error or the resume banner is up, and while focus is inside the chrome, so a keyboard user keeps the seek bar reachable (`D-061`'s other clause, kept). Pausing is now the deck button, the large play affordance, Space or `k`; a click on the picture only wakes the chrome. Web-only: no dependency, no server change, no contract change. Evidence: a new smoke step drives a real Chromium against the disposable instance — the bar and the deck read `opacity: 0` with `pointer-events: none` while playback advances, the picture keeps its height across the fade (283px), a click on the picture wakes the chrome without pausing, a move near the deck wakes it, and a move across the middle does not; each half was shown to be load-bearing by reverting it (no fade → `condition not met: chrome faded while playing`; click-to-pause restored → `clicking the picture paused playback; only the deck button and Space may`). Source: user report and instruction 2026-09-21 ("o player não some ... o pause é só se clicar no botão de pause ou espaço") + advisor `answered`, 2026-09-21.
- `D-065` — The watch page's chrome floats over the picture. The user's instruction ("o controle deve ficar por cima da imagem obviamente") reverses the other half of `D-061`: the tiled pane is gone, the picture is the whole player region (`absolute inset-0` over the `letterbox` shade), the bar sits over its top edge and the track chips, telemetry lines and transport deck sit over its bottom edge — one geometry in windowed and in fullscreen, so a hidden chrome leaves the picture full-bleed. Backing: the palette's own background at 90% with `backdrop-blur-xl` — the idiom the app's nav already uses, at a higher opacity because this chrome floats over media rather than over the app: against a white frame a flat 70% leaves `muted` at 2.41:1 and 85% at 4.16:1, while 90% clears the floor at 4.95:1, and over the bright `testsrc2` fixture the real pixels read `#141522` for the bar (`muted` 6.58:1) and `#13152d`–`#212221` for the deck (`muted` 5.81:1, `foreground` 9.09:1). (b) `chromeFocused()` pinned on any focus, and a mouse click leaves focus on the button it hit, so pressing fullscreen pinned the chrome forever; only `:focus-visible` (keyboard) focus pins now. Web-only — no dependency, no server change, no contract change; `D-057`'s full-width deck and `D-056`'s episode rail are untouched. Evidence: the smoke step asserts the geometry (the picture's rect equals the player region's, and the deck's top edge sits inside it), the fade, the wake paths, the click that must not pause, the deck click that must not pin and the scrub release — each shown to fail with its own part reverted (`the picture does not own the player region: video 65..348 vs region 0..493` for the tiled layout; `condition not met: chrome faded again after a scrub` without the effect; `condition not met: chrome faded again after a click on the deck` without the `:focus-visible` guard); plus four real-Chromium captures (windowed hidden, fullscreen shown, fullscreen hidden, fullscreen shown again) and pixel samples proving the picture runs behind the chrome's band when it is hidden (`#ffff05`/`#0000fa`, the fixture's own colours). Source: user instruction 2026-09-21 + advisor `answered`, 2026-09-21.
